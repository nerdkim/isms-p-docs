## Certification criterion

When introducing, developing, or changing an information system, secure coding methods shall be applied.

## Key checkpoints

1. Have coding standards for the secure implementation of the information system been established and applied?

## Detailed explanation

> * This item is a **relaxed certification criterion (Annex 7-3)** under the special case of Information Security Management System certification. The certification criterion and key checkpoints above are the relaxed/adjusted official text, while the detailed explanation, related laws, evidence, and nonconformity examples below are the content of the "ISMS-P Certification Criteria Guide" for Annex 7 [2.8.1 Definition of security requirements], the same control domain (under the relaxed criteria, they apply within the scope of the certification criterion and checkpoints above).

When newly introducing, developing, or changing an information system, procedures shall be established and implemented so that feasibility can be reviewed and the system can be accepted from the perspective of information security and personal information protection.

- When introducing a new information system (servers, network equipment, commercial software packages) and security systems, establish an introduction plan that includes an analysis of introduction feasibility and other matters
  - Analysis of current system resource utilization rate, usage volume, and capacity limits
  - Requirements for performance, stability, security, reliability, and compatibility and interoperability with existing systems
  - Compliance with legal requirements demanded by the Personal Information Protection Act (including the Notice on Standards for Measures to Ensure the Safety of Personal Information) and others, where the system falls under a personal information processing system
- Reflect information security and personal information protection requirements in the Request for Proposal (RFP) and use them as criteria when selecting vendors or products
- Establish system acceptance criteria for judging whether to accept the information system
  - Establish acceptance approval criteria that reflect the performance, security, legal requirements, and other matters defined when the introduction plan was established
  - Reflect the acceptance criteria in the purchase contract and other documents so that they are complied with during the system introduction process

When newly introducing, developing, or changing an information system, security requirements including legal requirements and the latest vulnerabilities shall be clearly defined and reflected from the design stage.

- Legal requirements related to personal information protection : access rights, access control, encryption, access records, etc.
- Information security and personal information protection requirements in accordance with the regulations of higher-level agencies and internal regulations
- Technical requirements related to information security : authentication, development security, etc.
- Latest security vulnerabilities, etc.

Coding standards for the secure implementation of the information system shall be prepared and applied.

- Prepare secure coding standards and conventions to minimize threats caused by known technical security vulnerabilities
- Include all relevant development languages and environments such as Java, PHP, ASP, web, mobile, etc.
- Conduct training for developers on secure coding standards and conventions

## Related laws

_No individual legal provision directly corresponding to this item is specified._

## Evidence (examples)

- Information system acceptance criteria and procedures
- Information system introduction RFP (Request for Proposal) and purchase contract
- Development deliverables (project execution plan, requirements definition document, screen design document, security architecture design document, test plan, etc.)
- Secure coding standards

## Nonconformity examples

- A case where security verification criteria and procedures before acceptance of an information system are not in place
- A case where internal regulations require reviewing the impact on the existing operating environment and security when introducing a new system, but for some recently introduced information systems detailed criteria and plans for security requirements at acceptance were not established, and accordingly a security review was not performed at acceptance
- A case where the internal development guidelines do not define the major security requirements related to development (authentication and encryption, security logs, etc.)
- A case where the "Development Standard Definition Document" specifies the use of unsafe encryption algorithms (MD5, SHA1) for user passwords, failing to properly reflect the relevant legal requirements
