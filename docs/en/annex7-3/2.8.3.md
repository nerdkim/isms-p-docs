# 2.8.3 Source Program Management  _( Annex 7-3 )_

## Certification criterion

Source programs must be managed so that only authorized users can access them.

## Key checkpoints

1. Are procedures established and implemented to control access to source programs by unauthorized persons?
2. Are change histories for source programs managed?

## Detailed explanation

> Note: This item is a relaxed certification criterion (Annex 7-3) under the special case of Information Security Management System certification. The certification criterion / key checkpoints above are the officially relaxed/adjusted text, while the detailed explanation / related laws / evidence / nonconformity examples below are the content of the "ISMS-P Certification Criteria Guide" for Annex 7 [2.8.5 Source program management], which is in the same control domain (under the relaxed criteria, they apply within the scope of the certification criterion / checkpoints above).

**Procedures to control access to source programs by unauthorized persons must be established and implemented.**

- Establish procedures for access to and use of source programs
- Grant access rights so that only authorized developers and staff can access, and block access by unauthorized persons
- Implement access control measures for the server where source programs are stored (configuration management server, etc.)

**Source programs must be safely stored in a location other than the operating environment in preparation for emergencies such as failures.**

- Back up and store the latest source programs and previous source programs
- Store/manage in a separate environment other than the operating environment
- Control access by unauthorized persons to source program backup copies

**Change histories for source programs must be managed.**

- Establish source program change procedures : approval and work procedures, version management approach, etc.
- Manage source program change history : change/implementation/migration dates, reason for change request, person in charge, etc.
- Perform change control over system-related documents (design documents, etc.) resulting from source program changes
- Perform periodic review of source program change history and change control records, etc.

## Related laws

_No individual legal provision directly corresponding to this item is specified._

## Evidence (examples)

- Operating status of configuration management systems such as SVN (list of persons with access rights, etc.)
- Source program change history

## Nonconformity examples

- Where no separate source program backup and configuration management system is established, and previous versions of source code are stored on the operating server or a developer's PC without approval or history management
- Where a configuration management system is established and operated, but access restriction to, and access and change history of, the configuration management system or the source code stored in it are not appropriately managed
- Where internal rules require source program version management through a configuration management system, but the latest version of the source program is stored only on a developer's PC and no separate backup is performed for it
