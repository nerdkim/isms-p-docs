# 2.10.4 Patch Management  _( Annex 7-3 )_

| Field | Value |
|---|---|
| Domain | 2. Protection Measure Requirements |
| Section | 2.10 System and Service Security Management |
| Item | 2.10.4 Patch Management |
| Criterion type | Annex 7-3 (Special provisions for certification, relaxed certification criteria) |

## Certification criterion

The latest patches shall be applied to prevent security incidents caused by vulnerabilities in information systems. However, if applying the latest patches is difficult after reviewing the impact on services, separate compensating measures shall be established and implemented.

## Key checkpoints

1. Are patch management policies and procedures for operating systems (OS) and software established/implemented according to the characteristics and criticality of each asset, such as servers, network systems, security systems, and PCs?
2. For key servers, network systems, security systems, etc., is the patch application status of installed OS and software managed periodically?
3. Where it is difficult to apply the latest patches to remediate vulnerabilities due to service impact and similar factors, are compensating measures in place?
4. For key servers, network systems, security systems, etc., is patching via public internet access restricted?
5. Where a patch management system is used, are sufficient protection measures such as access control in place?

## Detailed explanation

> ※ This item is a **relaxed certification criterion (Annex 7-3)** under the special provisions for information security management system certification. The certification criterion / key checkpoints above are the relaxed/adjusted official text, while the detailed explanation / related laws / evidence / nonconformity examples below are drawn from the "ISMS-P Certification Criteria Guide" content for Annex 7 [2.10.8 Patch Management], the same control area (under the relaxed criterion, they apply within the scope of the certification criterion / checkpoints above).

Patch management policies and procedures for OS and software shall be established/implemented according to the characteristics and criticality of each asset, such as servers, network systems, security systems, and PCs.

- Targets of patch application : servers, network systems, DBMS, application programs, commercial software, open source, security systems, PCs, etc.
- Patch cycle : reflecting asset criticality and characteristics
- Method of checking patch information
- Pre-review procedure before patch distribution
- Emergency patch application procedure
- Security review when patches are not applied
- Patch personnel and responsible person
- Contact information of patch-related vendors (manufacturers), etc.

For key servers, network systems, security systems, etc., the patch application status of installed OS and software shall be managed periodically.

- Manage as a list so that version information, patch application status, and application date per patch of the operating systems and software installed on key servers, network systems, security systems, etc. can be verified
- Periodically check whether the latest security patches need to be applied

※ Sites for checking the end of service support (EOS or EOL) date for major OS types (examples)
- MS Windows : https://support.microsoft.com/ko-kr/lifecycle/search
- Red Hat Linux : https://access.redhat.com/support/policy/updates/errata
- CentOS : https://wiki.centos.org/About/Product
- AIX : https://www-01.ibm.com/support/docview.wss?uid=isg3T1012517
- HP-UX : https://hpe.com/info/hpuxservermatrix
- Solaris : https://www.oracle.com/technetwork/server-storage/solaris/overview/releases-jsp-140987.html

Where it is difficult to apply the latest patches to remediate vulnerabilities due to service impact and similar factors, compensating measures shall be established.

- Since applying patches to operating systems may affect system availability, apply them after sufficiently analyzing the impact through impact analysis and other defined procedures, taking into account the criticality and characteristics of the operating system
- Where immediate patch application is difficult depending on the operating environment, establish the reasons and additional compensating measures, report them to the responsible person, and manage the status

For key servers, network systems, security systems, etc., patching via public internet access shall be restricted.

- However, where unavoidable, establish protection measures through prior risk analysis and apply them after approval by the responsible person

Where a patch management system (PMS) is used, since it can be abused as a malware distribution point to internal-network servers or PCs, sufficient protection measures such as access control shall be established for the patch management system server, management console, etc.

- Access control measures for the patch management system itself : blocking access by anyone other than authorized administrators, changing default passwords, removing security vulnerabilities, etc.
- File integrity checks when distributing update files, etc.

## Related laws

- Personal Information Protection Act Article 29 (Duty of Safety Measures)
- Standards for Measures to Ensure the Safety of Personal Information Article 9 (Prevention of Malicious Programs, etc.)

## Evidence (examples)

- Patch application management policy/procedure
- Patch application status by system
- Impact analysis results related to patch application

## Nonconformity examples

- Where, on some systems, OS patches have not been applied for a long period without a valid reason or approval by the responsible person
- Where some systems are using an OS version whose service support has ended (EOS), but no corresponding response plan or compensating measures have been established
- Where the latest patches are applied for commercial software and OS, but no procedure or assigned personnel exist for checking and applying the latest patches for open source programs (openssl, openssh, Apache, etc.), so the latest security patches are not applied
