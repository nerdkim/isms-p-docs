# 2.7.1 Definition of Security Requirements  _( Annex 7-2 )_

## Certification criterion

When introducing, developing, or changing an information system, security requirements such as legal requirements related to information security and personal information protection, the latest security vulnerabilities, and secure coding methods shall be defined and applied.

## Key checkpoints

1. When newly introducing, developing, or changing an information system, are feasibility review and acceptance procedures from the information security and personal information protection perspectives established and implemented?
2. When newly introducing, developing, or changing an information system, are security requirements including legal requirements and the latest vulnerabilities clearly defined and reflected from the design stage onward?
3. Are coding standards for the secure implementation of an information system established and applied?

## Detailed explanation

> Note: This item is a **relaxed certification criterion (Annex 7-2)** under the special provisions for information security management system certification. The certification criterion / key checkpoints above are the officially relaxed/adjusted text, while the detailed explanation / related laws / evidence / nonconformity examples below are drawn from the content of the "ISMS-P Certification Criteria Guide" for the same control domain, Annex 7 [2.8.1 Definition of Security Requirements] (under the relaxed criteria, they apply within the scope of the certification criterion / checkpoints above).

When newly introducing, developing, or changing an information system, procedures shall be established and implemented so that feasibility from the information security and personal information protection perspectives can be reviewed and the system can be accepted.

- When introducing a new information system (server, network equipment, commercial software package) and security system, establish an introduction plan that includes matters such as an introduction feasibility analysis
  - Analysis of the utilization rate, usage volume, and capacity limits of current system resources
  - Requirements for performance, stability, security, reliability, and compatibility and interoperability with the existing system
  - Where it corresponds to a personal information processing system, compliance with legal requirements demanded by the Personal Information Protection Act (including the Notice on Standards for Measures to Ensure the Safety of Personal Information)
- Reflect the requirements from the information security and personal information protection perspectives in the request for proposal (RFP) and use them as criteria when selecting a vendor or product
- Establish system acceptance criteria to judge whether to accept the information system
  - Establish acceptance approval criteria that reflect the performance, security, legal requirements, etc. defined when the introduction plan was established
  - Reflect acceptance criteria in the purchase contract, etc. so that they are complied with during the system introduction process

When newly introducing, developing, or changing an information system, security requirements including legal requirements and the latest vulnerabilities shall be clearly defined and reflected from the design stage onward.

- Legal requirements related to personal information protection : access rights, access control, encryption, access records, etc.
- Information security and personal information protection requirements according to the requirements of higher-level institutions and internal regulations
- Technical requirements related to information security : authentication, development security, etc.
- The latest security vulnerabilities, etc.

Coding standards for the secure implementation of an information system shall be prepared and applied.

- Prepare secure coding standards and conventions to minimize threats arising from known technical security vulnerabilities
- Include all relevant development languages and environments such as Java, PHP, ASP, web, mobile, etc.
- Conduct training for developers on the secure coding standards and conventions

Note: Software development security methodology (example)

&lt;Source&gt; Software Development Security Guide (Ministry of the Interior and Safety, KISA)

## Related laws

_No individual legal provision directly corresponding to this item is specified._

## Evidence (examples)

- Information system acceptance criteria and procedures
- Information system introduction RFP (request for proposal) and purchase contract
- Development deliverables (project execution plan, requirements definition document, screen design document, security architecture design document, test plan, etc.)
- Secure coding standards

## Nonconformity examples

- Where criteria and procedures for security verification prior to information system acceptance have not been prepared
- Where internal regulations are in place to review the impact on the existing operating environment and the security when introducing a new system, but for some recently introduced information systems no detailed criteria and plans for security requirements at acceptance were established, and consequently no security review was performed at acceptance
- Where major security requirements related to development (authentication and encryption, security logs, etc.) are not defined in the internal guidelines related to development
- Where the "Development Standard Definition Document" requires user passwords to be used with an insecure encryption algorithm (MD5, SHA1), thereby failing to appropriately reflect the relevant legal requirements
