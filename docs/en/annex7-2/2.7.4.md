# 2.7.4 Source Program Management  _( Annex 7-2 )_

## Certification criterion

Source programs shall be managed so that only authorized users can access them, and as a rule shall not be stored in the operating environment.

## Key checkpoints

1. Are procedures established and implemented to control access to source programs by unauthorized persons?
2. Are source programs stored safely in a location other than the operating environment in preparation for contingencies such as failures?
3. Is the change history of source programs managed?

## Detailed explanation

> Note: This item is a **relaxed certification criterion (Annex 7-2)** under the special provisions for information security management system certification. The certification criterion / key checkpoints above are the official text as relaxed/adjusted, while the detailed explanation / related laws / evidence / nonconformity examples below are drawn from the "ISMS-P Certification Criteria Guide" for the same control area, Annex 7 [2.8.5 Source Program Management] (under the relaxed criteria, they apply within the scope of the certification criterion / checkpoints above).

**Procedures to control access to source programs by unauthorized persons shall be established and implemented.**

- Establishment of procedures for access to and use of source programs
- Granting access rights so that only authorized developers and personnel can access them, and blocking access by unauthorized persons
- Access control measures for the server (configuration management server, etc.) where source programs are stored

**Source programs shall be stored safely in a location other than the operating environment in preparation for contingencies such as failures.**

- Backup storage of the latest source programs and previous source programs
- Storage/management in a separate environment other than the operating environment
- Access control by unauthorized persons over source program backup copies

**The change history of source programs shall be managed.**

- Establishment of source program change procedures : approval and work procedures, version management methods, etc.
- Management of source program change history : dates of change/implementation/migration, reasons for change requests, responsible persons, etc.
- Performing change control over system-related documents (design documents, etc.) resulting from source program changes
- Performing periodic reviews of source program change history and change control records, etc.

## Related laws

_No individual legal provision directly corresponding to this item is specified._

## Evidence (examples)

- Operational status of configuration management systems such as SVN (list of access authorized persons, etc.)
- Source program change history

## Nonconformity examples

- The case where a separate source program backup and configuration management system is not in place, and previous versions of source code are stored on the operating server or developer PCs without approval and history management
- The case where a configuration management system is built and operated, but access restriction and access/change history for the configuration management system or the source code stored in it are not properly managed
- The case where internal regulations require source program version management through a configuration management system, but the latest version of the source program is stored only on a developer PC and no separate backup is performed for it
