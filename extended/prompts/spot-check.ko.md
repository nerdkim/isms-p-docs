# S8. 제출 내용 점검(ISMS-P 상 문제가 있는가)

> English: [spot-check.md](spot-check.md)

`system-grounding.ko.md`를 먼저 적용한 뒤 사용합니다. Codex와 Claude Code에서는 함께 제공되는 skill
`skill/isms-p-review/SKILL.md`가 이 시나리오를 실행하며, manifest 앞에 routing 표
(`skill/isms-p-review/topic-index.json`)를 둡니다.

```
[작업] 사용자가 전달한 내용(정책/절차 발췌, 운영 실태 설명, 시스템/설정 설명, 화면 설명, 사고 내용, 계약 조항 등)이 ISMS-P 인증기준상 문제가 되는지 판정하십시오. 문제가 없을 수도 있으며, 그 경우 그렇게 답합니다.

입력:
- 전달 내용: {{텍스트 / 파일 경로 / 설명}}
- 적용 세트: {{별표7 / 별표7의2 / 별표7의3}} (없으면 별표 7로 두고 그 사실을 표기)

[절차]
1. 개인정보 게이트: 입력에 실제 개인정보(주민등록번호, 전화번호, 이메일 등)로 보이는 값이 있으면 반복하지 않고 [masked]로 대체한 뒤 몇 건을 가렸는지 적는다.
2. 입력을 단언(무엇을 어떻게 하는지, 정하는지, 설정하는지, 빠뜨리는지에 대한 구체적 문장)으로 나눈다. 주어진 맥락과 알 수 없는 점을 적는다.
3. 읽기 전에 routing 한다. 단언을 extended/manifest.json(적용 세트의 한국어 항목, name과 subgroup)과, 별표 7이면 extended/index/defect-rulebook.json에 대조해 1차 항목 8개 안팎을 고르고 나머지는 관련 항목으로 적는다. docs/ 전체 grep은 하지 않는다.
4. 1차 항목의 docs/ko .md를 전부 읽는다(영어 mirror는 사용자가 영어로 일할 때만).
5. 1차 항목마다 주요 확인사항을 하나씩 단언에 대조해 표시한다: 충족 근거 있음 / 미충족 / 정보 부족 / 해당 없음. 그 뒤 항목 하나에 판정 하나를 준다. 결함 후보(미충족이 하나 이상. 단언, 확인사항 번호, 일치하는 결함사례를 인용), 확인 필요(미충족은 없지만 관련 확인사항이 정보 부족. 증적자료 절에서 판단에 필요한 증적을 나열), 문제 없음(관련 확인사항이 모두 충족 또는 해당 없음. 분명히 그렇게 쓴다), 범위 외(실제 우려이지만 자료집이 정하지 않는 것: 법규 해석, 2026 개편, 의무 대상과 절차). 정보 부재는 확인 필요이며 문제 없음이 아니다. 중결함/경결함을 매기지 않고, 항목 원문에 없는 수치를 말하지 않는다.
6. 걸리는 항목이 없으면 "자료집으로 보는 한 전달 내용은 ISMS-P 인증기준에 닿지 않습니다"라고 분명히 쓰고 무엇을 찾아봤는지 나열한다.
7. 관련 법규는 항목의 줄을 그대로 인용하고 해석하지 않는다. 표기가 인증기준 안내서 2023.11.23 기준이며 이후 개정은 반영되어 있지 않다고 한 번 적는다.

[출력] templates/spot-check.ko.md 양식(존댓말)으로 대화에 답한다. 한 줄 결론을 먼저 쓴다. 표의 모든 행과 근거 항목마다 docs/ko/<세트>/<번호>.md > <섹션>을 인용한다.
파일은 사용자가 기록을 남기자고 할 때만 쓴다: extended/outputs/spot-checks/spot-check-<주제>-<날짜>.md, 그리고 결함 후보가 있거나 법규 쟁점이 있으면 extended/outputs/review-queue/<날짜>-spot-check.md 에 한 줄 추가.
```
